已验证的机制

  1. 未知选项连带损失测试目录。pytest -n 未预置，遇到它后整个剩余 argv 进入 opaque。旧版 heuristic 碰巧把 -n 当带值选项，因此 tests/devices 可以独立匹配。5277:42 的旧预测383.23秒、新预测1.36秒，实际368.89秒，是明确的退步例子。保守停止是避免错误猜测的策略，但在规则缺口大时会损失预测信息。
  2. 核心入口未在查询时强制保留。core 约束了建节点；查询只要求节点特征是 query 的子集。来自其他 Python 执行方式的 tool=python 节点仍可被选中。主榜30条中15条涉及此节点，历史3193条、中位数1.333秒；其中10条旧版也已命中该根节点。缩减方差风险给此节点的分数2.413低于pytest专门节点约3.17–3.26。仅在诊断查询中强制保留 core，可把代表病例从1.333秒改到3.568秒，仍远低于数百秒，说明不能只修这一处。
  3. “精确节点”统计包含更具体命令。subset coverage 汇总所有包含节点特征的训练命令。无位置参数不是一个显式特征，导致“全量运行”和“指定一个测试”共用父节点。unittest 的64条相同特征记录中位数86.408秒，被82条更具体记录（中位数0.726秒）拉到2.103秒。精确命中 shortcut 直接使用这个已经混合的统计；此现象两后端、两版本都存在。
  4. 工作量和运行状态仍不足。pytest目录名没有表达测试数量、参数化规模；同一个repo含不同task对应版本，解释器路径被归一化，依赖、缓存、last-failed状态没有进入本次离线特征。证据包括同形 pytest -q tests 只有33.50/51.89秒两条训练记录，却出现390–415秒执行；这里不能断言究竟是哪个环境因素造成差异。
  5. 未知工具和条件执行叠加。cargo fmt只借到了唯一cargo test的538.52秒记录，而真实环境没有rustfmt。make install-dev-rs缺乏专门历史，实际Rust构建575.34秒，合成器仍把未执行的test-rs计入。当前串行合成假设保留阶段都会执行，不能预测失败导致的短路。
